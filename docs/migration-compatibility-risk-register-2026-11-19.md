**Disposition: REVIEW REQUIRED — NOT APPROVED FOR PRODUCTION.**

This register is a source-level inventory of the 61 candidate migration files listed by the identity V2 CI workflow. It records the principal object/operation surface and identifies migrations requiring heightened production-parity review. It is not a substitute for a complete SQL semantic review, production schema comparison, historical-row disposition, or replay against a restorable production-like clone. The current live database baseline recorded in the 19 November readiness review is 178 migrations ending at `20261114174204`; none of this candidate chain is recorded as production-applied.

## Review rules

- Treat all 61 migrations as unapplied candidate SQL. CI applies them only to a disposable baseline.
- `CREATE TABLE IF NOT EXISTS` does not prove an existing production table has the expected columns, constraints, indexes, owner, RLS or grants.
- Every `CREATE OR REPLACE FUNCTION` requires signature, owner, SECURITY DEFINER, search_path, dependency and EXECUTE-grant comparison against production.
- Every ALTER/DROP/trigger replacement requires an object-existence check and a before/after data and behavior comparison.
- Do not run this chain against production as a diagnostic. Use a restorable clone first.
- The CI workflow's filename list is the source of truth for ordering; do not infer order from filesystem sorting.

## Connected production parity observations — read-only, 19 November 2026

The connected production project was queried read-only after the 61-file manifest correction:

- Migration history: **178 applied migrations**, latest `20261114174204`.
- Candidate V2 objects: **0 of 18 sampled candidate tables** and **0 of 6 sampled candidate RPCs** exist in the live `henvalt` schema.
- Existing legacy populations are not empty: 4 Shopify connections across 3 tenants (therefore at least one tenant has multiple connections), 3 customers, 5 sessions, 2 session aliases, 2 checkouts, 166 canonical events, 30 OAuth state rows, 5 opportunities, 5 recovery interventions, 5 delivery attempts, 4 provider events and 16 pixel keys. `shopify_privacy_requests` had 0 rows at inspection time. All 4 Shopify connections are marked active, but 3 of 4 lack `shopify_shop_id`, `access_token_secret_ref` and `refresh_token_secret_ref`; only one row has the shop ID and both token references. None of the four rows is currently marked `reauth_required_at`, and the three incomplete active rows are therefore not automatically signalled as requiring reauthorization. This is a material identity/runtime readiness gap, not merely a migration issue. A read-only join to `pixel_keys` shows all 16 legacy pixel-key rows belong to that one token-backed connection (1 active, 15 inactive); the other three active connection rows have no pixel keys. This does not establish that the remaining token-backed store is controlled by the current app owner or suitable as the V2 test store. All 30 existing OAuth state rows are expired (21 consumed, 9 expired and unconsumed); there were 0 unexpired, unconsumed states at inspection time.
- Live `shopify_connections` does not yet contain the candidate `app_key` column; live `shopify_oauth_states` likewise does not contain candidate `app_key`. Candidate migrations 001 and 003 add these fields. The four existing connection rows and 30 OAuth state rows therefore require an explicit identity/expiry disposition; do not assume they automatically become V2-owned installations. Migration 001 adds `shopify_connections.app_key` as nullable and deliberately does not backfill it; its new route-token and webhook-inbox tables require a valid app-registry identity. Existing connections cannot be treated as V2-ingress-ready until an owner-controlled registry entry and explicit reauthorization/identity mapping are verified.
- One of the four legacy connection rows stores a non-`myshopify.com` host (`hencalt.mystore.com`). The V2 OAuth `validShop()` parser and webhook inbox domain constraint accept canonical `*.myshopify.com` shop identities only. Resolve this row from trusted Shopify shop metadata or quarantine it; never substitute a storefront custom domain as the OAuth shop identifier.
- Live `customers`, `sessions`, `session_aliases`, `checkouts` and `canonical_events` do not yet contain `shopify_connection_id`. Migration 007 adds these columns as nullable, deliberately performs no historical backfill, and adds composite foreign keys as `NOT VALID`. Existing legacy rows will therefore remain unresolved (NULL lineage) unless a separately reviewed reconciliation is performed. Never infer exact store identity from tenant, email, checkout token or session reference alone.
- The existing legacy tables and row counts mean this is not an empty-database install. Migration 007's deliberate no-backfill design is protective, but the cutover must explicitly quarantine or map legacy rows and prove V1 writers cannot create mixed lineage during promotion.
- Migration 010 alters only the candidate `shopify_checkout_identity_v2` table, which is absent in production; it adds a token non-empty CHECK and explicitly drops/recreates the candidate token unique index. This is a candidate-table dependency, not an existing live checkout-table rewrite.
- No production DDL, DML, function deployment, secret access/change or workflow modification was performed by these queries.
